## Lens (verbatim)

> CROSS-SYSTEM. Multi-process, multi-machine, multi-thread and multi-runtime interactions: concurrent writers to shared files (sessions JSONL, sqlite stores, config, the fff-search frecency LMDB, KG thesaurus files) from two agent processes or agent plus MCP server; file-lock fallbacks and fs::rename across filesystems; two tokio runtimes plus rayon in one process (UF-033); the MCP server over stdio and streamable HTTP with concurrent requests; CI hosts (bigbox runner, ubuntu-latest, macOS) differing in page size, glibc vs Apple Libc locking, AVX2 paths; timezone or locale dependent canonicalisation; signal handling and process exit ordering (Drop not run, daemon threads, the Miri leak-check observation on rayon); self-update replacing a running binary; env inheritance into child processes (Command::env) and the terraphim_server child used by tests; orphaned server processes (#281) sharing ports and sqlite files with tests.

## Facts established during the round (load-bearing for several ideas)

- **Transport correction.** The lens names "streamable HTTP"; the binary wires rmcp `SseServer` (`/sse` plus `/message`, crates/terraphim_mcp_server/src/main.rs:252-295) or stdio (:307). Every idea below says SSE. In SSE mode `McpService` is cloned per connection (main.rs:295); every field is an `Arc`, so clones alias one state (phase1_notes/G).
- **bigbox facts** (queried 2026-09-12 by `ssh bigbox`): x86_64, 4096-byte pages, AVX2 present, glibc 2.39, 24 cores. The audit host is aarch64 macOS with 16 KiB pages and Apple Libc. `.github/workflows/ci.yml:57` runs `--lib` only; `.gitea/workflows/native-ci.yml:73` runs `--bins --tests --examples`, so `crates/terraphim_mcp_server/tests/test_find_files.rs` (the in-CI exercise of the fff-search mapping path) runs on bigbox only, not on "both runners" as EXP-104's notes say.
- **The frecency tracker is opened and never read.** `rg -n frecency crates/terraphim_mcp_server/src/lib.rs` returns only lines 102-135: `McpService::new` opens `FrecencyTracker::open` when `FFF_FRECENCY_PATH` is set and exposes it through `frecency()`, but no `FilePickerOptions` receives it and no tool handler calls it. The reachable LMDB surface for EXP-207 is therefore `open_env` (fff-search dbs/lmdb.rs:146-175: `unsafe { EnvOpenOptions::new() ... .open(path) }` with `map_size` and `max_dbs` only, default LMDB flags, lock file on, TLS readers) plus `open_database_safe`; there is no later traversal to extend the harness with.
- **heed refuses a double open.** heed 0.22.1 keeps a process-wide `OPENED_ENV` registry keyed by canonical path (envs/mod.rs:39, env_open_options.rs:403) and returns `Error::EnvAlreadyOpened` (lib.rs:175), so LMDB's "one environment per process per path" rule is enforced in Rust, not left to the caller.
- **One bundled SQLite, two wrappers, one threading mode.** `libsqlite3-sys` 0.30.1 is built with `-DSQLITE_THREADSAFE=1` (build.rs:137, serialised mode) and reaches the process through both rusqlite 0.32.1 (terraphim_sessions, terraphim-session-analyzer, terraphim_persistence) and sqlx-sqlite 0.8.6 (opendal). Neither wrapper calls `sqlite3_config` on the workspace path (`rg sqlite3_config` over the two crates: only rusqlite's opt-in `trace::config_log`, which no workspace code calls). The second `libsqlite3-sys` node in `cargo tree -d` is the host-side copy inside `sqlx-macros-core` (`cargo tree -e normal -p sqlx-macros-core | rg sqlite` lists sqlx-sqlite and libsqlite3-sys), the same host proc-macro instance that broke Phase 3's `CFLAGS=-fsanitize=thread` build.
- **The single `Mmap::map` site and its gates.** fff-search 0.8.4 has exactly one mapping call, types.rs:640 in `get_cached_content`; its two callers are `get_content_for_search` (types.rs:655-667) and `warmup_mmaps` (file_picker.rs:1909-1928). Both reach the `count >= max_files` check at types.rs:631 before the map, and `self.content.get()` (types.rs:614) can only be `Some` after a previous map. With `max_files: 0` the check is `0 >= 0` and returns `None`, so the Phase 8 Delta 2 remediation closes every mapping path statically.
- **The AVX2 verify kernel is untested upstream.** `verify_dispatch` (case_insensitive_memmem.rs:352-366) takes `verify_avx2` only when `needle_lower.len() >= 32` on x86_64 (and `verify_neon_dotprod` when `>= 16` on aarch64). The crate's five unit tests (:564-662) use needles of at most 26 bytes, so `verify_avx2` has no upstream test, and nothing in this workspace has executed it (the audit host is aarch64). `search` and `search_packed_pair` are `pub` (lib.rs:107), so a harness can call the kernels directly.

- **I-324** NO_EVIDENCE with rationale. libgit2 maps packfiles through `git_mwindow`, and status over a packed HEAD tree reads them; but `git gc`, `git repack` and `git maintenance` write new packs to temporary names, `rename` them in and `unlink` the old ones, never truncating in place, so an existing mapping stays valid on Linux and macOS (the inode survives until unmapped). A hostile repository that does truncate is EXP-205's crafted-repo arm.
- **I-325** NO_EVIDENCE. `git2::Repository::discover` calls `git_repository_discover` with the caller's ceiling list only; libgit2 consults `GIT_DIR`, `GIT_WORK_TREE` and `GIT_CEILING_DIRECTORIES` solely under `GIT_REPOSITORY_OPEN_FROM_ENV`, which fff-search does not request (`rg -n 'open_from_env|OPEN_FROM_ENV' fff-search-0.8.4/src` = 0). The env reads libgit2 does perform at init (`HOME`, `XDG_CONFIG_HOME`) are UF-001's reader and are covered.
- **I-326** INAPPLICABLE. Every canonicalisation is `str::to_lowercase`/`to_ascii_lowercase` (Unicode, locale-independent); there is no `Local::now` or `chrono::Local` outside tests, no `setlocale` in the process (libgit2, SQLite and LMDB do not call it), and jiff reads `TZ` through std's locked `env::var`. Nothing in the workspace changes meaning with `LC_ALL` or `TZ`.
- **I-327** ALREADY_COVERED with a correction for the lead. EXP-104's notes say the mapping path "executes on both runners" via `test_find_files.rs`; `.github/workflows/ci.yml:57` is `--lib`, so that binary runs only under `.gitea/workflows/native-ci.yml:73` on bigbox (x86_64, 4 KiB threshold, so nearly every source file maps), never on ubuntu-latest, macos-latest (16 KiB threshold) or windows-latest (where `get_cached_content` is a stub, types.rs:589-596). The GitHub matrix's `test` job therefore never executes fff-search's mapping path at all.
- **I-328** ALREADY_COVERED (phase4 lead addendum 2; phase8 section 1). Both coverage lanes run plain `cargo llvm-cov --workspace --lib --ignore-run-fail` in-process on glibc; a SIGBUS from an EXP-104-class event in a lib test would drop that binary's profile silently. `test_find_files` is an integration test and is not in the `--lib` set, so the coverage lanes do not exercise the mapping path either.
- **I-329** INAPPLICABLE. `update_history.json` timestamps are `chrono::DateTime<Utc>` per machine (state.rs), the scheduler compares against the local clock, and phase 3 already records bigbox's clock offset as a logging caveat. No memory-relevant consumer of a timestamp exists.
- **I-330** NO_EVIDENCE; resource note. Each `grep_files` call builds its own `FilePicker` (lib.rs:1372), so K concurrent SSE clients yield K `spawn_git_status` threads (file_picker.rs:801, each owning its `Repository`, `!Sync` enforced), K read-only mappings of the same files (shared page cache, no aliasing between mappings of immutable content) and K increments of libgit2's init refcount (git2 never calls `git_libgit2_shutdown`, so the count only grows; the `Once` at libgit2_sys::init runs the sysdir env reads once). The cost is threads and address space, not UB; the writer-under-mapping case is EXP-302.

## Notes for Phase 5 (instrument recipe for every bundled-C ASan run on bigbox)

1. Build with `RUSTFLAGS="-Zsanitizer=address" cargo +nightly build -Zbuild-std --target x86_64-unknown-linux-gnu` and `CFLAGS="-fsanitize=address -fno-omit-frame-pointer"`.
2. For a standalone harness (EXP-205/206/207, EXP-301) no proc-macro links libsqlite3-sys, so plain `CFLAGS` is safe.
3. For a workspace binary that links sqlx (EXP-302: terraphim_mcp_server; also terraphim-agent, terraphim-cli) plain `CFLAGS` instruments the host copy of libsqlite3-sys inside `sqlx-macros-core` and the host link fails exactly as in Phase 3. Use a `CC` wrapper script that adds `-fsanitize=address` only when the `-o` path lies under `target/x86_64-unknown-linux-gnu/` (target artefacts) and not under `target/debug/build/` or `target/release/build/` (host artefacts). `CFLAGS_x86_64_unknown_linux_gnu` does not help because host and target triples are equal.
4. Admissibility check before reading any result: `nm <target-dir>/build/libgit2-sys-*/out/build/*.o | rg -c __asan_` (and the same for `libsqlite3-sys-*/out/sqlite3.o` and `lmdb-master-sys-*/out/*.o`) must be non-zero, and the same count over `target/debug/build/libsqlite3-sys-*` (host) must be zero. A clean ASan run without that check is NEEDS_REFINEMENT, not NO_EVIDENCE (the Phase 3 lesson).
5. Record `uptime` load and `pgrep -c terraphim_server` (#281 orphans) in every log header, as phase8_remediation_plan.md section 12 asks.
