# ADR 001: Release-Signing Key Rotation and Multi-Key Verification

Status: Accepted

Date: 2026-07-07

## Context

- Terraphim client binaries (`terraphim-agent`, `terraphim-grep`, `terraphim-cli`) self-update and verify downloaded archives with an Ed25519 public key embedded at compile time (`terraphim_update::signature::EMBEDDED_PUBLIC_KEYS`).
- The originally embedded key (`1uLjooBMO+HlpKeiD16WOtT3COWeC8J/o2ERmDiEMc4=`, generated 2025-01-12 in the `terraphim-ai` era) was **never used to sign any archive** — the signing step was never wired into the release pipeline. Its private half is not recoverable from the Terraphim 1Password Connect vault or disk; it is treated as lost.
- A dedicated keypair for the (now-extracted) `terraphim-clients` repo exists in 1Password as *"Terraphim Clients zipsign Release Key 2026-07"* (`op://Terraphim/bfrac6ue7mlp7xrgjstymjyn5m/zipsign_private_key_base64`). Its public half is `iW2sM72/09yfiQ3jMB2GBALCRN+1FLLgD5qBbISFfS0=`. The private key is properly stored; the public key was verified to sign+verify a real archive end-to-end.
- Workflows must sign archives from the very next release, and already-deployed binaries (embedding only the 2025 key) must still be able to reach a state where they can verify signed archives.

## Decision

1. **Rotate the primary embedded key** to the 2026-07 clients key. Keep the 2025-01-12 key in the trusted list as a **legacy fallback** so any archive ever signed with it (none today) would still verify.
2. **Multi-key verification**: `verify_archive_signature` tries every key in `EMBEDDED_PUBLIC_KEYS` and returns `Valid` on the first match. The GitHub fallback (`self_update` `verifying_keys`) receives the full key list, not a single key. This makes future rotations non-breaking.
3. **Private key handling**: the private key stays in 1Password and is materialised into CI only via the `ZIPSIGN_PRIVATE_KEY` GitHub Actions secret (base64, 64-byte seed‖pubkey). It is never committed. `scripts/sign-release-archives.sh` decodes it to a `chmod 600` temp file and removes it on exit.
4. **Bridge-update posture**: the updater keeps **warn-and-proceed** on `MissingSignature` (unsigned archives). Pre-rotation deployed binaries (2025 key, warn-and-proceed code) can therefore update from a final unsigned release to a binary embedding the new key set; from the following release onward, archives are signed and verify against the new key. The flip from warn-and-proceed to hard-reject on `MissingSignature` is deferred to a follow-up once signed releases are established.
5. **Explicit-key path stays strict**: when a caller passes a single key explicitly, decode/length errors propagate (no silent skip) — only the embedded multi-key list is validated leniently so a malformed legacy entry cannot brick verification.

## Consequences

- **Positive**: signing ships without breaking already-deployed binaries (the bridge update via warn-and-proceed). Future rotations require only appending a new key to the list — no coordinated flag-day cut-over.
- **Positive**: a tampered archive (signature present, no trusted key matches) is rejected (`Invalid`); only genuinely unsigned archives hit `MissingSignature`.
- **Negative / residual risk**: until the follow-up flips `MissingSignature` to reject, HTTPS transport integrity to `downloads.terraphim.ai` remains the sole integrity control for any unsigned archive. This is acceptable for the transition window and matches the pre-existing posture.
- **Negative**: already-deployed binaries embedding only the 2025 key cannot verify 2026-07-signed archives directly; they require the one-time bridge update. For a pre-1.0 product with a small installed base this is acceptable (manual reinstall is the fallback).
- **Operational**: rotating the signing key in future means (a) generate a new keypair, (b) append its public half to `EMBEDDED_PUBLIC_KEYS`, (c) add the private half to 1Password + CI secret, (d) ship one release signed with the new key while the old key remains trusted, (e) remove the old key from the list only after sufficient rollout.

## Alternatives considered

- **Pivot to a freshly generated keypair (option B)**: rejected — the 2026-07 key already exists, is properly stored, and was purpose-made for this repo. No reason to generate a third key.
- **Single-key verifier (replace, no legacy)**: rejected — loses forward compatibility and provides no defence-in-depth for any future signed-with-old-key artifact.
- **Hard-reject `MissingSignature` immediately**: rejected — would strand every deployed binary on the first signed release. Deferred to a follow-up.
